接入索引

三个只读接口，没有账号、没有密钥、没有 SDK。你能做的第一件事不是「申请接入」， 而是自己验一遍——所以这里把验证写成了三行命令。

接口

端点返回用途
/api/ledger/items全部条目，每条带 prev_hash / hash拿走数据
/api/ledger/verify{ok, first_bad, chain_tail, genesis}看服务端自检结果
/api/ledger/export导出件原文，它的 sha256 就是锚值校验的基准
 
# 自己算锚值，再去 /ledger 页面对一眼
curl -s https://drawcommons.org/api/ledger/export | sha256sum

这里故意不印锚值。写死一个校验值，它迟早与文本漂移，而「印出来的校验值 对不上自己吐出的字节」正是这类站点最不该犯的错。上面这条命令，任何时候跑都算得出当下的真值。

四个示例

01 · 验链

Python 3.8+，零依赖。重算哈希、查链、比对锚值。
看它报警：--tamper

python3 verify.py

02 · 消费

Node 18+，零依赖。统计后生成一段可嵌入的 HTML 卡片，带署名。

node summarize.mjs

03 · 巡检

POSIX sh + curl。每天一行记录，退出码区分「正常／链坏／取不到」。

./check.sh

04 · MCP

Python 3.8+，零依赖。三个只读接口包成 MCP tool，装进 Claude／Cursor； ledger_verify 在本机重算，不采信服务端的 ok。

python3 selftest.py

示例 4 是本轮新增的：账本天然适合做成 MCP——只读、无鉴权、三张表一条链， 模型自己取数比人把数字粘进对话更可靠。但别把它的 verdict: agree 读成 「内容可信」：它验的是字节未变，不是事情发生过。

三条边界

一、验哈希用 Python，别用 JS 重写。Python 的 json.dumps(2.0) 是 "2.0"，JS 的 JSON.stringify(2.0) 是 "2"。同一份数据算出 两个哈希，你会得到一个假的「校验失败」，然后开始怀疑数据——而数据是对的。

二、账本记的是申报与确认，不是事实本身。链完整只证明「这份记录与入链时一致」， 不证明「这件事真的发生过」。

三、现在是 beta。字段与口径都会变，rule_version 就是干这个的。真要把数据用于 决策，等到 30 日公示期满、协议生效之后。
