# 需求单（request）· v2.2 草案

> 状态：**草案（`x-spec-version` 2.2.0-draft.1）**，随 r6 出件升 `2.2.0`。
> 配套文件：`request.schema.json`（一行状态记录的规范）、`../ddl_v1.4.sql`（表结构与约束）。

## 0. 一句话

账本记「已经给了什么」，需求单记「还缺什么」。**两者不是同一张表，也不是同一条链。**

## 1. 为什么不进哈希链

哈希链只有一个用途：让「某条记录没有被改写」成为任何人可自行验证的事实。它靠 append-only 成立——写进去的字节永远不动。

需求是**意图**：可以撤回、可以过期、可以被认领后作废。把它塞进链里，只有两条路：

- 让链允许改写 → 链就不再是链，锚值失去意义；
- 或把每次状态变化都写成新条目 → 锚值会随「有人发了个需求」而抖动，而锚值的价值恰恰在于**不因日常活动而变**。

所以需求单单独一张表：**append-only，但不入链、不计入锚值**。状态变化写新行（`seq` 递增），公开视图取每组最大 `seq`。这样「历史不可改」与「状态可前进」两件事同时成立，不必二选一。

### 1.1 同一条原则：草案也不进协议

顺着这条往下推一步：既然**意图**不该进账本，那么「还没决定发不发」的草案就更不该。

agent 往往比人更早发现缺口——它每天撞墙，墙就是需求。但它判断不了「这个缺口说出去对主人有没有代价」。所以草案停在会话里：agent 拟稿、附证据，人点头，才发 `open`。

这也是**不加 `draft` 状态**的理由。`draft` 会把「还没决定的事」写进协议，而协议只记已决定的事实；草案的生命周期属于客户端，不属于表结构。加了它，迟早会有人拿 `draft` 行当「已存在的需求」来统计，而那个数字没有意义。

## 2. 状态机

```
       ┌──────── withdrawn（发布方撤回，终态）
       │
open ──┼── claimed ── delivered ── closed（终态）
       │      │  ↑         │  ↑
       │      └──┘         └──┘ 被拒收后再交一次（v1.7）
       │      回退（v1.6；发布方或当前认领方）
       │
       └──── expired（到期仍没人交，终态；open 与 claimed 两支都走这里）
```

| 迁移 | 允许 | 条件 |
| --- | --- | --- |
| `open → claimed` | ✅ | 必须给出 `claim_agent_id`，且该主体已登记公钥。**不能顺带改条款**：请求体带了 `category` / `need_desc` / `window_expires_at` / `note` 之一且与上一行不等 → `DGB_LED_037`（v1.6） |
| `claimed → delivered` | ✅ | 必须有 `occurred_at` 与 `evidence_uri`；这一次同时产出两条账目（§6）。**认领方必须是当初认领的那个人**（换人交付 = 绕过先到先得，`DGB_LED_037`），条款同样不能改 |
| `delivered → closed` | ✅ | 双签完成、两条账目已入链——**由受方那次确认顺手写入**，没有「关闭」这个接口 |
| `open / claimed → withdrawn` | ✅ | 只有发布方能撤 |
| `claimed → open` | ✅ | **回退**（v1.6）：发布方或**当前**认领方都能提，认领人由此有了退路。只改状态，条款沿用上一行，`claim_agent_id` 与 `claimer_email` 置空 |
| `delivered → delivered` | ✅ | **再交一次**（v1.7）：只在前一条 `delivered` 行**已被拒收**时成立。它是真正的第二轮交付，要重新过条款比对，认领方仍须是当初那个人；未被拒收的重复提交走重试（`already`）或 `DGB_LED_029` |
| `open → expired` | ✅ | 到期后由**写入面顺带结算**（`Writer.sweep_expired`，进程启动一次、每次真写前一次），非人工、没有接口。到期时刻：填了 `window_expires_at` 就是它，空串按 `created_at + 90 天`（v1.6，见 §4②） |
| `claimed → expired` | ✅ | **逾期作废**（v1.7）：同一支时钟，口径与 `open` 一样（填了按截止、空串按本行 `created_at + 90 天`，也就是「认领后 90 天」）。写的是 `expired` 而不是 `withdrawn`——撤回是发布方签名的意思表示，时钟没有签名 |
| 其他任意组合 | ❌ | `DGB_LED_020` |

`closed` 不开放直写，理由是它能被**判定**：两条账目在链上、受方对那条 `give` 签过名，这两件事一发生，条件就齐了。开一个「关闭」接口，就等于让某人有权宣布一件系统已经挣到的事——也能宣布一件还没挣到的事，而这两种请求在接口上长得一模一样。所以关单是确认的副产品（见 §6 末段），不是一个动作。

三条终态（`closed` / `withdrawn` / `expired`）不得再有后继行（`DGB_LED_020`，与其余非法迁移同一个码）。
`delivered → delivered` 也不是「同一状态可以无限追加」：它的前置条件写死在触发器里——上一行
必须有一条**指向它**的拒收记录（`request_reject.seq = 上一行 seq`）。没有拒绝，就没有下一轮。`seq` 必须从 1 起连续（`DGB_LED_021`）——跳号意味着有一个状态被跳过了，那正是审计该抓的东西。

## 3. 字段

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `request_id` | `rq_[0-9a-z]{8,32}` | 发布方生成，库内唯一约束兜底 |
| `seq` | 整数 ≥1 | 行内序号，连续，不跳号 |
| `state` | 六枚举 | 见 §2 |
| `category` | 字符串 | 与账本条目同一词表（compute / bandwidth / device / venue / labor…） |
| `need_desc` | 字符串 1–2000 | 缺什么、要多少、什么条件下算交付。**只写事不写人** |
| `window_expires_at` | 字符串 | 空串＝**默认发布后 90 天到期**（v1.6；v1.5 及以前是「无期限」）。填了则不得晚于发布 + 90 天（`DGB_ING_009`）：**窗口最长 90 天**，与「不填按 90 天算」是同一个常数（`MAX_WINDOW_DAYS`）。库里这一列存什么就读出什么——空串不会在写入时被改写成具体时间 |
| `requested_by` | `party_id` | 可假名，但必须有主体 |
| `claim_agent_id` | `party_id` 或 null | `claimed` 起必填 |
| `evidence_uri` | 字符串或 null | `delivered` 起必填 |
| `occurred_at` | 时间或 null | `delivered` 起必填 |
| `created_at` | 时间 | 服务端盖章，不接受客户端自带。记的是**本行**落库时间，不是首行时间——公开视图的 90 天规则作用在 `closed` / `withdrawn` 行上，「之后 90 天从列表隐藏」才成立 |
| `note` | 字符串或 null | null 在公开页显示为「无备注」 |
| `poster_email` | 字符串或 null | **发布方联系方式**（v1.7）。发布那一行给，之后每行沿用；空串存 NULL。**不进任何公开视图**：匿名读者看不到，只有这条单的两方经签名读口才取得到（§6.1） |
| `claimer_email` | 字符串或 null | **认领方联系方式**（v1.7）。认领或交付那一行第一次填，之后沿用；回退到 `open` 时清空（认领关系作废，那个地址属于一个已经不在单上的人）。同样不进公开视图 |

不含金额字段。与 `entry.schema.json` 同样的理由：需求描述「缺什么、缺多久」，不描述「值多少钱」。

## 4. 三个决定

**① 需求可以匿名发布，但不能没有主体。**
`requested_by` 必填，而 `party` 表默认 `display_mode='pseudonymous'`——所以「匿名」指**不展示实名**，不是「不登记主体」。理由很实在：认领之后要走双签，签名主体必须是登记过公钥的 `party`；无主体的需求进库只会变成一条永远 `open` 的噪声。

**② 需求单不物理删除，只收窄可见性。**
`closed` / `withdrawn` 的状态行保留 90 天后从**列表**隐藏，`expired` **立即**不公开（v1.5 起，理由见下），三者都 `/r/<id>` 永久可访问并显示状态。理由是这两条都不成立：删除会破坏 `seq` 连续性（等于删了历史），而长期挂着过期需求会让列表变成坟场。存储成本可以忽略：一行几十字节。
90 天是常量不是条款，改它不需要换版；改「是否保留」才需要。

`expired` 为什么不跟另外两类共用 90 天：v1.4 写这条时 `expired` 根本不会自动产生（当时没有触发者），三类共用 90 天没暴露问题。v1.5 让写入面开始真的结算 `expired`，一旦共用 90 天，一张过了截止的单会**因为**被结算成终态而重新回到列表，再等 90 天才走——正好把要清的东西又摆回来。差别在信息量：`closed` / `withdrawn` 记的是真发生过的事，值得在架上待一阵；`expired` 是从没人接，列它没有信息量。

未认领的单另按两条收窄（v1.5，2026-11-16）：填了 `window_expires_at` 的，过了截止时刻即不再公开；没填的（空串），自 `created_at` 起 90 天即不再公开。同样只影响**列表与发现口**（`/requests`、`/api/v1/requests`），`/r/<id>` 不变。

**v1.6 起两支合流：都真的走到 `expired`，差别只剩「到期时刻怎么算」。**

- 填了 `window_expires_at`：到期时刻就是它；
- 没填（空串）：到期时刻 = `created_at + 90 天`。

两支都由 `Writer.sweep_expired` 写 `expired`：它是 `open → expired` 唯一的写入者，不看请求体、没有调用方能指名哪一单。它不是一个角色，是一个时钟。写出来的行 `created_at` 是当前时刻，按上一条立即从列表收走，`/r/<id>` 显示「已过期」，不再可接。

**这一条推翻了 v1.5 的说法**「空串＝无期限，时钟不替人改主意」。改的理由是那句话在站点上留了一个死角：没填截止的单永远 `open`，`/r/` 永远说「可接」，只是从列表消失——「看不见但还活着」，知道 id 的人仍能认领。默认期限把这死角关掉。代价是发布方失去「永久挂牌」这个选项；想长期挂着就把截止写远一点，而不是不写。

**~~截止只约束「还没人接」那一段。~~（v1.7 推翻）** v1.6 写的是「一旦变成 `claimed`，截止时刻不再触发任何动作」：`sweep` 只扫 `open`，视图也只在 `state='open'` 时按截止收窄。那条在页面上留了一个死角——认领方接了不交，单子永远停在「已认领」，发布方等到截止也等不到下一步，而时钟每跑一次都从它身上跨过去。

v1.7 起 `sweep` 也扫 `claimed`，到期同样写 `expired`。**为什么不是 `withdrawn`**：撤回是发布方签名的意思表示，时钟没有签名；替人写一条「他撤回了」就是伪造。作废与撤回在页面上都读作「不能接了」，但在账上是两件事——一件有人认，一件没人认。

**为什么不再给 `claimed` 单加一个「交付期限」列。** 到期口径沿用同一个：填了 `window_expires_at` 就是它，空串就是「本行 `created_at` + 90 天」。claimed 行的 `created_at` 是认领时刻，所以空串在这里读作「认领后 90 天」——不是「发布后 90 天」。同一个常数，两段不同的时间，不必再多一列、再多一套「没填时按什么算」的规则。

90 与终态那句 90 同类：常量不是条款，改它不换版。改「要不要默认期限」才换版。

**③ `mutual_id = "m-" + request_id`。**
好处：不需要第二个发号器，且从任一账目可反查它来自哪张需求单。代价：需求单与账目的对应关系被公开——**这一点是故意的**，需求单本来就是公开的，藏起来反而制造「有一层看不见的关联」。
因此 `mutual_id` 有两代格式并存：历史是 `m-<任意>`，v2.2 起是 `m-rq_<...>`。约束只对新格式生效（`DGB_LED_028`），历史条目不追改——追改就是重写历史。

## 5. 双签：签什么

被签的是**条目哈希**，不是条目 JSON。载荷逐字节如下（UTF-8、LF、无 BOM）：

```
drawcommons-confirm-v1\n<entry_id>\n<entry_hash>\n
```

签名容器用 OpenSSH 的 SSHSIG：`ssh-keygen -Y sign -n drawcommons-confirm`，与仓库 tag 签名同一套工具链（ED25519 + `allowed_signers`），不新增任何依赖。

四种载荷/容器组合实测：

| 实验 | 结果 | 说明 |
| --- | --- | --- |
| SSHSIG 签 hash 文本（正确 namespace） | ✅ 通过 | 签名 314 B，ASCII armor，可直接存 `TEXT` 列 |
| namespace=git 的签名拿来验确认 | ❌ 拒绝，`namespace does not match` | 域隔离由签名容器保证，不靠人记得 |
| `g_9` 的签名挪去验 `g_10`（hash 相同） | ❌ 拒绝 | 载荷含 `entry_id`，条目间不可重放 |
| SSHSIG 签规范化 JSON | ✅ 通过 | 但换成「第三方自己的序列化」（`json.dumps` 默认带空格）即 ❌ 拒绝 |
| raw Ed25519（64 B） | ✅ 通过 | 任何语言 3 行可验，但不含 namespace，域隔离须由载荷前缀自担 |

选 hash 的三条理由：

1. **hash 已覆盖全部字段**（`sha256(prev_hash + "\n" + canonical(entry))`），签 hash 等于签整条记录，且不必让验签方实现同一套 canonical JSON——上面第 4 行就是这一步的代价：签 JSON 时，验签方编造字节的方式差一个空格就验不过。
2. **域隔离是现成的**：SSHSIG 的 namespace 由容器校验，不是口头约定。
3. **与既有工具链同源**：`ssh-keygen -Y verify -f allowed_signers -I <party_id> -n drawcommons-confirm`。

一条不能省的顺序：**先重算 hash → 与条目 `hash` 比对 → 再验签**。
签名只证明「某人签过这 32 字节」，证明「这条记录没被改」靠重算。反过来做（先验签、后重算）等于承认签名者对一段可能已被篡改的内容背书。

确认的落点与失败的处理：

- **确认不改条目，也不改 `verifiability`。** `verifiability` 是条目表的列，而条目 `hash` 覆盖全部字段、表 append-only——改这一列等于改 `hash`，链当场就断（见 §6「为什么签名不进条目表」）。所以「有人认过这条」单独存在 `entry_confirm`，导出时并到顶层 `confirmations` 数组里，与 `items` 并列。条目字节一个都不动，锚值只因为多了这一段而变。`verifiability` 因此**永远停在 `self_reported`**——它记的是「这条是谁说的」，不是「有多少人认过」。
- **验签失败直接拒写，不落一条「差一点的确认」。** 四种拒绝：`DGB_LED_030`（条目不存在）、`DGB_LED_031`（签名主体不是这条 `give` 的受方）、`DGB_LED_034`（签名与按条目重算的 `hash` 对不上）、`DGB_LED_035`（这条已经确认过、不覆盖也不撤销）。理由不是严格，是**没有第二条路**：确认一旦落库就只有「有」和「没有」，没有「撤销」，所以一条错签名留在库里就是一条永远修不掉的错话。拒写是唯一不留下假话的选项——客户端可以重签，重签是幂等的、不产生新记录。

## 6. 与账本的连接

`claimed → delivered` 这一次状态写入，**同时**产生两条账目。两条都不是客户端提交的，是从那条已经签过名的 `delivered` 行**推出来**的：

| 账目 | id | 字段从哪来 |
| --- | --- | --- |
| `give` | `g-<request_id>` | `from_agent_id` = `claim_agent_id`（认领方）；`to_agent_id` = `requested_by`（发布方）；`category`、`occurred_at` 照抄；`quantity`/`unit` 留 null（需求单没有数量字段，编一个数就是造假） |
| `receive` | `r-<request_id>` | `state='delivered'`、`occurred_at` 照抄、`evidence_uri` 照抄 |

两条同 `mutual_id = "m-" + request_id`，所以「一次互助」在账本里就是这一对。id 也是派生的、不带随机尾缀：任何拿到公开需求单的人都能算出这两个 id，不需要问运营方要一份对应表。

`give` 的给方是认领方，不是发布方——给东西的是那个把事做完的人。这也让 `/api/v1/entry` 那条「give 的给方必须就是签名主体」在转换里同样成立：提交 `delivered` 的就是认领方，转换用的是他的签名。

**为什么 `evidence_uri` 只在 `receive` 上。** 两件事的举证方不同：`give` 说「我给了什么」，是给方自述；`receive` 说「这次交付有凭据」，而凭据要受方认——第 04 步那条确认签的正是 `give` 的 `hash`。把凭据塞进 `give`，会让「给了什么」与「凭什么说给了」混在同一行。

`receive.evidence_uri` 与 `request.evidence_uri` 是**同一份值被复制**，不是引用链。两处各自独立可验；「指针的指针」在审计时只会多一层不信任。

**为什么签名不进条目表。** 签名签的是条目 `hash`，而 `hash` 又覆盖条目的全部字段——把签名放进条目就成了循环（`hash` 覆盖签名、签名覆盖 `hash`）。所以确认单独一张表 `entry_confirm`，它指向条目而不属于条目。副作用是好的：条目哈希完全不因「有人确认了」而变，确认可以被拒绝、可以被重签，账目一动不动。

**两个人各签了一次，但签的不是同一样东西。** 认领方签的是那条 `delivered` 提交（外层信封，`drawcommons-ingest` 域），`receive` 是它的函数；发布方签的是 `give` 的 `hash`（`drawcommons-confirm` 域）。所以 `receive` 没有第二次确认这一档——不是留待将来，是**不需要**：再签一次，签的还是同一句话。

**重复提交同一次交付怎么办。** 分两种，后果不同：

- **字段全一致** → 这是重试（网络断了、没收到响应）。回 `200` 与 `already: true`，附上上次那两条账目的位置与 hash，一个字节都不再写。重试不该被当成错误——那会让客户端以为交付失败了，而它其实成功过。
- **字段有一处不一致** → 这不是重试，是想改已入账的凭据。回 `422 DGB_LED_029`，凭据以第一次为准。append-only 本来也不给改的机会，但要说清是「不让改」而不是「撞车了」。

两条账目与那条 `delivered` 行在**同一个事务**里落库。分成两步就会留下「已交付但账上没东西」的中间态，而那个中间态没有任何人能修：`delivered` 不能重进（状态机不许），补账又没有入口。

**被拒收之后再交一次（v1.7）。** 拒收只把「沉默」变成一句否认，单子仍停在 `delivered`，唯一出口是 `closed`——于是拒收一个不合要求的交付，等于把这张单钉死。v1.7 允许在**被拒收之后**再交：追加一条 `delivered` 行、再生成一对账目。三次判断的顺序是：

1. 当前 `closed` → 一律走重放（单子封了，任何提交都只能是重试）；
2. 当前 `delivered` 且**没有**指向这一行的拒收 → 走重放：字段一致回 `already`，不一致回 `029`；
3. 当前 `delivered` 且**有**拒收 → 这是一次新的交付，追加行与账目。

**账目 id 怎么排。** 第一轮沿用历史的 `g-rq_…` / `r-rq_…`，第二轮起带 `-d<n>`（`n` = 该单第几条 `delivered` 行）。不给所有轮次都加后缀：库里已有的条目就叫那个名字，改格式等于让历史条目换 id，而链上的 id 不可改。两种格式并存不是妥协，是「旧的那一次已经发生过」。

**`DGB_LED_032` 因此从「一互助一条」改成「一互助的条数不超过交付次数」。** 约束没有变松，只是把「一次」换成「一次一对」：同一轮重复入账永远是 `1 = 1`，写不进去；第二轮 `1 < 2`，写得进去。

**关单。** 发布方对那条 `give` 确认成功之后，这一单自动写一行 `closed`（完整复制上一行，只换 `state`——`DGB_LED_024` 要求 `closed` 也带 `occurred_at` 与 `evidence_uri`，关单不能把交付凭据弄丢）。这一步没有自己的接口，理由见 §2。

**受方不认怎么办（v1.6）。** 交付那一刻两条账目已经进链，账本 append-only 撤不回来——把单子改成别的状态，会让人以为那次交付被取消了。所以「拒收」不是状态，是一层并列的断言（`request_reject`），和 `entry_confirm` 同一个位置：确认是「我认可这条 `give`」，拒收是「我不认这次交付」。两者都不改被指的东西。

它只做一件事：把「沉默」变成「有签名、有理由、可查询的拒绝」。在此之前，受方不满意只有「不签 confirm」这一种表达，而那和「忘了签」在库里长得一模一样。状态仍停在 `delivered`，`/r/<id>` 多一行「受方已拒收」与理由；公开视图多一列 `rejected`（0/1），列表上能看出这单有争议。

签名载荷三行（`drawcommons-reject` 域，与确认那个域分开——共用一个域就会出现「把确认签名挪来当拒收」这条路，而它验得过）：

```
drawcommons-reject-v1
<request_id>
<seq>
```

`seq` 指向被拒的那条 `delivered` 行，不是「当前状态」——单子将来若被放回、重新认领、再交付一次，一次拒收指的仍然是它拒过的那一次。只签 `request_id` 的话，一次拒收会漂到这张单的所有交付上。

只有发布方能签（`DGB_LED_036`）；只能拒当前那条 `delivered` 行；**一次交付只能被拒一次**，不可改（`DGB_LED_012/013`）。v1.6 时主键是 `(request_id)`，一单一条；v1.7 改成 `(request_id, seq)`——多轮交付就要能多轮拒收，否则第二轮被拒时写不进去。

**拒收之后单子不会自己走向任何终态**——账已经记了，状态机没有「撤销已发生的事」这条路。它停在那里，等着被看见；被看见之后，发布方可以确认（若那一轮其实可接受），认领方可以再交一次（若还能改），时钟到期则作废。

**催告层（v1.7）。** 认领方在交付之后可以留一条「我催过」：`request_reminder`，同样是一层并列断言，不改状态、不改条款。它填的是「发布方一直不确认」这段沉默里唯一缺的东西——在此之前，认领方除了等没有别的动作，而页面上那个「催告」键按下去只会改本地清单。载荷三行（`drawcommons-remind` 域，与拒收分开——两者都落在同一条 `delivered` 行上，共用一个域就会出现「把催告签名挪来当拒收」这条路）：

```
drawcommons-remind-v1
<request_id>
<seq>
```

绑 `seq` 不绑时间：催告的对象是「这一次交付还没被确认」，绑时间会让同一次催告在重发时变成新记录。真实时刻由服务端盖章。同一张单同一认领方 **24 小时一次**，写在触发器里（`DGB_LED_038`）——这是「别刷屏」，不是业务判断，放应用层就会被脚本绕过；只有当前认领方能签（`DGB_LED_039`）。

### 6.1 联系方式：进库、不进公开面

页面上写着「双方认领后才可见」。这句话要成立，得同时做到三件事，缺一件就是空话：

1. **存得下。** `request` 行上加两列（`poster_email` / `claimer_email`），不是 `party` 上加一列。
   理由：这是**这一单**的联系方式，不是一个人的主联系方式。放 `party` 会让每次发单被迫共用
   一个地址，也让公开主体多出一列可被枚举的隐私。
2. **传得对。** 发了那行给 `poster_email`，认领或交付那行第一次给 `claimer_email`，之后每行
   沿用。带了就必须与上一行一字不差（`DGB_LED_037`）——这版没有编辑功能，推进状态不是改
   联系方式的暗门。回退到 `open` 时清空认领方邮箱：那个地址属于一个已经不在单上的人。
3. **看不见。** 两列**都不进任何公开视图**。`v_public_request` 的列是显式写的，天然不带；
   `v_request_current` 是 `SELECT r.*`，v1.7 重建它才会带上——那是给写入面与鉴权读口用的。

**为什么不做在网页上。** `/r/<id>` 匿名可读、站点 `script-src 'none'`，浏览器里没有可验证的
身份。把邮箱渲染上去就是公开；做一个「输入 party_id 就给你看」的表单，等于谁都能冒充。
所以它走写入面那套签名：

```
GET /api/v1/request/contact?id=<request_id>
X-DG-Party / X-DG-Issued / X-DG-Nonce / X-DG-Sig      # 与写口同一套信封
```

验过签名才知道「问的人是谁」，再由 `contact_for()` 判定他是不是这条单的两方之一，且这条单
是否已经有人认领（`claimed` / `delivered` / `closed`）。三种失败——单不存在、不是你的事、
还没人认领——**一律同一个 404**，不区分。区分它们就等于给了一个探测接口：「这个 id 存在吗」
「谁接过这单」。

## 7. 结构落在哪里

表结构分六份：`../ddl_w4.sql`（v1.3 基线）→ `../ddl_v1.4.sql` → `../ddl_v1.5.sql`（可见性收窄）→ `../ddl_v1.6.sql`（回退、拒收层、视图两列）→ `../ddl_v1.7.sql`（联系方式、再交一次、催告层、claimed 到期）→ `../ddl_v1.8.sql`（签名存证五列与三条触发器）。

**必须按序执行**：v1.5 / v1.6 / v1.7 都用 `DROP VIEW` + `CREATE VIEW` 重建视图，后跑的覆盖先跑的。v1.7 还多一处顺序依赖——它先重建 `request_reject` 表，而 `ALTER TABLE … RENAME` 会把所有引用旧表的触发器与视图**一起改写**成旧表名，所以状态机触发器与 `v_public_request` 都必须在那之后重建。`evidence/build_ledger.py` 把这六份写在一个元组里，不靠调用方记得。

### 7.1 签名存证（v1.8）

每一行状态都记下**写下它的那次请求**的签名：逐字载荷（`sig_payload`）、SSHSIG（`sig`）、
签名者指纹（`sig_key_fp`），外加一个说明来历的 `sig_ref`。读口是
`GET /api/v1/requests/<id>/evidence`。

**它证明什么、不证明什么**，写在 `ddl_v1.8.sql` 头部，这里只留一句：证明「这一行来自
那把钥的这一次请求」，不证明「每个字段逐字等于请求体」。后者做不到，因为请求体原文
不留存——留了就是把一份可能含联系方式的原文钉进只增不删的表。

`evidence` 三类：`http`（有签名）、`derived`（时钟结算的 `expired`、确认派生的
`closed`；**禁止**带签名，`DGB_LED_042`）、`none`（v1.8 之前的行，当时没存，
`trg_request_no_update` 也不许补）。仍**不进链**：存证不是上链，锚值不因这一版改变。

本节只写「为什么是这几条约束」，不重复贴 SQL——同一段 SQL 贴两处，早晚会有一处是旧的；判据脚本直接执行那些文件，文档与实现因此没有第二个版本。

六组约束，各有各的失败形态：

| 组 | 拦什么 | 错误码 |
| --- | --- | --- |
| 状态机 | 跳号、非法迁移、终态再写、第 1 行不是 `open` | `DGB_LED_020` / `021` |
| 字段完备 | `claimed` 无认领方、`delivered` 缺时间或证据 | `DGB_LED_023` / `024` |
| 发布方固定 | 同一单的第 2 行换了个 `requested_by` | `DGB_LED_025` |
| 主体存在 | `requested_by` / `claim_agent_id` 未在 `party` 登记 | `DGB_LED_019` |
| 拒收层 | 认领方或第三方替你拒收、同一条交付拒两次 | `DGB_LED_036` / `012` / `013` |
| 催告层 | 发布方催自己、第三方替你催、24 小时内刷第二条 | `DGB_LED_039` / `038` / `012` / `013` |
| append-only | 对 `request` 的 `UPDATE` / `DELETE` | `DGB_LED_012` / `013` |

`seq` 的连续性与状态迁移拆成两个触发器，且迁移触发器里带了 `seq = max+1` 前置条件。原因是 SQLite 对同表多个 `BEFORE INSERT` 触发器不保证执行顺序：两条同时满足时，报 020 还是 021 看运气，而「错误码确定」本身是判据的一部分。

两个视图：

- `v_request_current`：每组取最大 `seq`，是「当前状态」的唯一口径；
- `v_public_request`：在它之上收窄两件事，**不删行**——① `closed` / `withdrawn` 按 90 天常量收窄、`expired` 立即不收；② `open` 单到期（有截止按截止时刻，无截止按发布 + 90 天）不再公开。公开页与 API 只查这个视图。现行定义在 `../../spec/ddl_v1.6.sql`（v1.5 与 v1.6 都用 `DROP VIEW` + `CREATE VIEW` 重建；视图不是快照，重建不改任何数据行，对已在跑的库立刻生效）。② 另有一个写入者：`Writer.sweep_expired` 会把到期的 `open` 与 `claimed` 单写成 `expired`（v1.7 起后者也进候选），视图收窄在它之前只是兜底。`claimed` 不按截止收窄——它已经有人接了，列表上仍然要看得见，直到时钟把它结算掉。
- v1.6 起该视图末尾多两列：`unconfirmed_days`（只对 `delivered` 有值，其余为 NULL——填 0 会被读成「当天确认了」）与 `rejected`（0/1，拒收层有没有记录）。加列不改任何 `WHERE`，v1.5 的口径一个字没动。

## 7.1 怎么把记录送进来

状态行与条目都经写入面提交，契约在 **`ingest.md`**：请求体自签（SSHSIG，
namespace `drawcommons-ingest`）、四条 POST、`DGB_ING_*` 错误码。本文件只管
「记录长什么样」，那份只管「怎么送」——两件事分开写，是为了改其中一件时不必动另一件。

三条与本文件相关的硬约束（在那份里执行）：第 1 行必须是 `open`；非第 1 行的 `open` 只有
一个来源——`claimed` 的回退（v1.6），所以重复提交首发 `open` 仍会被状态机挡下
（`DGB_LED_020`）；`closed` 与 `expired` 不接受直写——前者要等双方签名与两条账目都落库，
后者由时钟结算。

## 7.2 谁来按这个键（责任，不是权限）

接口能验的是「这把钥签了这条请求」，验不了「这个人同意公开这件事」。两件事在 r6 里
都只剩最后一下，按给人：

| 动作 | 替人做会怎样 |
| --- | --- |
| 发需求（`open`） | 公开宣布「我这里缺东西」。append-only，`withdrawn` 只是状态，正文永久可读 |
| 认领（`claimed`） | 替人答应交付；占的是人的时间，不是 agent 的 |

所以 agent 该做的是「识别 + 拟稿 + 附证据」，不该做的是「代替他说我需要」或「代替他
答应给」。这一条**不进 DDL**——它是约定，执行者在客户端。写在这里是因为它约束的是
协议的使用方式，而使用方式也会被审计：一条由 agent 刷出来的需求，事后看不出与人发的
有什么区别，除非当初就说清「最后一下是人按的」。
