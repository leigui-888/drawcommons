# 需求单（request）· v2.2 草案

> 状态：**草案（`x-spec-version` 2.2.0-draft.1）**，随 r6 出件升 `2.2.0`。
> 配套文件：`request.schema.json`（一行状态记录的规范）、`../ddl_v1.4.sql`（表结构与约束）。

## 0. 一句话

账本记「已经给了什么」，需求单记「还缺什么」。**两者不是同一张表，也不是同一条链。**

## 1. 为什么不进哈希链

哈希链只有一个用途：让「某条记录没有被改写」成为任何人可自行验证的事实。它靠 append-only 成立——写进去的字节永远不动。

需求是**意图**：可以撤回、可以过期、可以被认领后作废。把它塞进链里，只有两条路：

- 让链允许改写 → 链就不再是链，锚值失去意义；
- 或把每次状态变化都写成新条目 → 锚值会随「有人发了个需求」而抖动，而锚值的价值恰恰在于**不因日常活动而变**。

所以需求单单独一张表：**append-only，但不入链、不计入锚值**。状态变化写新行（`seq` 递增），公开视图取每组最大 `seq`。这样「历史不可改」与「状态可前进」两件事同时成立，不必二选一。

### 1.1 同一条原则：草案也不进协议

顺着这条往下推一步：既然**意图**不该进账本，那么「还没决定发不发」的草案就更不该。

agent 往往比人更早发现缺口——它每天撞墙，墙就是需求。但它判断不了「这个缺口说出去对主人有没有代价」。所以草案停在会话里：agent 拟稿、附证据，人点头，才发 `open`。

这也是**不加 `draft` 状态**的理由。`draft` 会把「还没决定的事」写进协议，而协议只记已决定的事实；草案的生命周期属于客户端，不属于表结构。加了它，迟早会有人拿 `draft` 行当「已存在的需求」来统计，而那个数字没有意义。

## 2. 状态机

```
       ┌──────── withdrawn（发布方撤回，终态）
       │
open ──┼── claimed ── delivered ── closed（终态）
       │       │            │
       │       └────────────┴── 不合法：认领后不能直接变成 open
       │
       └──── expired（窗口到期未认领，终态）
```

| 迁移 | 允许 | 条件 |
| --- | --- | --- |
| `open → claimed` | ✅ | 必须给出 `claim_agent_id`，且该主体已登记公钥 |
| `claimed → delivered` | ✅ | 必须有 `occurred_at` 与 `evidence_uri`；这一次同时产出两条账目（§6） |
| `delivered → closed` | ✅ | 双签完成、两条账目已入链——**由受方那次确认顺手写入**，没有「关闭」这个接口 |
| `open / claimed → withdrawn` | ✅ | 只有发布方能撤 |
| `open → expired` | ✅ | 由窗口到期触发，非人工 |
| 其他任意组合 | ❌ | `DGB_LED_020` |

`closed` 不开放直写，理由是它能被**判定**：两条账目在链上、受方对那条 `give` 签过名，这两件事一发生，条件就齐了。开一个「关闭」接口，就等于让某人有权宣布一件系统已经挣到的事——也能宣布一件还没挣到的事，而这两种请求在接口上长得一模一样。所以关单是确认的副产品（见 §6 末段），不是一个动作。

三条终态（`closed` / `withdrawn` / `expired`）不得再有后继行（`DGB_LED_020`，与其余非法迁移同一个码）。`seq` 必须从 1 起连续（`DGB_LED_021`）——跳号意味着有一个状态被跳过了，那正是审计该抓的东西。

## 3. 字段

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `request_id` | `rq_[0-9a-z]{8,32}` | 发布方生成，库内唯一约束兜底 |
| `seq` | 整数 ≥1 | 行内序号，连续，不跳号 |
| `state` | 六枚举 | 见 §2 |
| `category` | 字符串 | 与账本条目同一词表（compute / bandwidth / device / venue / labor…） |
| `need_desc` | 字符串 1–2000 | 缺什么、要多少、什么条件下算交付。**只写事不写人** |
| `window_expires_at` | 字符串 | 空串＝无期限；公开页必须显示为「无期限」 |
| `requested_by` | `party_id` | 可假名，但必须有主体 |
| `claim_agent_id` | `party_id` 或 null | `claimed` 起必填 |
| `evidence_uri` | 字符串或 null | `delivered` 起必填 |
| `occurred_at` | 时间或 null | `delivered` 起必填 |
| `created_at` | 时间 | 服务端盖章，不接受客户端自带。记的是**本行**落库时间，不是首行时间——公开视图的 90 天规则作用在终态行上，「终态之后 90 天从列表隐藏」才成立 |
| `note` | 字符串或 null | null 在公开页显示为「无备注」 |

不含金额字段。与 `entry.schema.json` 同样的理由：需求描述「缺什么、缺多久」，不描述「值多少钱」。

## 4. 三个决定

**① 需求可以匿名发布，但不能没有主体。**
`requested_by` 必填，而 `party` 表默认 `display_mode='pseudonymous'`——所以「匿名」指**不展示实名**，不是「不登记主体」。理由很实在：认领之后要走双签，签名主体必须是登记过公钥的 `party`；无主体的需求进库只会变成一条永远 `open` 的噪声。

**② 需求单不物理删除，只收窄可见性。**
`closed` / `withdrawn` / `expired` 的状态行保留 90 天后从**列表**隐藏，`/r/<id>` 永久可访问并显示状态。理由是这两条都不成立：删除会破坏 `seq` 连续性（等于删了历史），而长期挂着过期需求会让列表变成坟场。存储成本可以忽略：一行几十字节。
90 天是常量不是条款，改它不需要换版；改「是否保留」才需要。

**③ `mutual_id = "m-" + request_id`。**
好处：不需要第二个发号器，且从任一账目可反查它来自哪张需求单。代价：需求单与账目的对应关系被公开——**这一点是故意的**，需求单本来就是公开的，藏起来反而制造「有一层看不见的关联」。
因此 `mutual_id` 有两代格式并存：历史是 `m-<任意>`，v2.2 起是 `m-rq_<...>`。约束只对新格式生效（`DGB_LED_028`），历史条目不追改——追改就是重写历史。

## 5. 双签：签什么

被签的是**条目哈希**，不是条目 JSON。载荷逐字节如下（UTF-8、LF、无 BOM）：

```
drawcommons-confirm-v1\n<entry_id>\n<entry_hash>\n
```

签名容器用 OpenSSH 的 SSHSIG：`ssh-keygen -Y sign -n drawcommons-confirm`，与仓库 tag 签名同一套工具链（ED25519 + `allowed_signers`），不新增任何依赖。

四种载荷/容器组合实测：

| 实验 | 结果 | 说明 |
| --- | --- | --- |
| SSHSIG 签 hash 文本（正确 namespace） | ✅ 通过 | 签名 314 B，ASCII armor，可直接存 `TEXT` 列 |
| namespace=git 的签名拿来验确认 | ❌ 拒绝，`namespace does not match` | 域隔离由签名容器保证，不靠人记得 |
| `g_9` 的签名挪去验 `g_10`（hash 相同） | ❌ 拒绝 | 载荷含 `entry_id`，条目间不可重放 |
| SSHSIG 签规范化 JSON | ✅ 通过 | 但换成「第三方自己的序列化」（`json.dumps` 默认带空格）即 ❌ 拒绝 |
| raw Ed25519（64 B） | ✅ 通过 | 任何语言 3 行可验，但不含 namespace，域隔离须由载荷前缀自担 |

选 hash 的三条理由：

1. **hash 已覆盖全部字段**（`sha256(prev_hash + "\n" + canonical(entry))`），签 hash 等于签整条记录，且不必让验签方实现同一套 canonical JSON——上面第 4 行就是这一步的代价：签 JSON 时，验签方编造字节的方式差一个空格就验不过。
2. **域隔离是现成的**：SSHSIG 的 namespace 由容器校验，不是口头约定。
3. **与既有工具链同源**：`ssh-keygen -Y verify -f allowed_signers -I <party_id> -n drawcommons-confirm`。

一条不能省的顺序：**先重算 hash → 与条目 `hash` 比对 → 再验签**。
签名只证明「某人签过这 32 字节」，证明「这条记录没被改」靠重算。反过来做（先验签、后重算）等于承认签名者对一段可能已被篡改的内容背书。

确认的落点与失败的处理：

- **确认不改条目，也不改 `verifiability`。** `verifiability` 是条目表的列，而条目 `hash` 覆盖全部字段、表 append-only——改这一列等于改 `hash`，链当场就断（见 §6「为什么签名不进条目表」）。所以「有人认过这条」单独存在 `entry_confirm`，导出时并到顶层 `confirmations` 数组里，与 `items` 并列。条目字节一个都不动，锚值只因为多了这一段而变。`verifiability` 因此**永远停在 `self_reported`**——它记的是「这条是谁说的」，不是「有多少人认过」。
- **验签失败直接拒写，不落一条「差一点的确认」。** 四种拒绝：`DGB_LED_030`（条目不存在）、`DGB_LED_031`（签名主体不是这条 `give` 的受方）、`DGB_LED_034`（签名与按条目重算的 `hash` 对不上）、`DGB_LED_035`（这条已经确认过、不覆盖也不撤销）。理由不是严格，是**没有第二条路**：确认一旦落库就只有「有」和「没有」，没有「撤销」，所以一条错签名留在库里就是一条永远修不掉的错话。拒写是唯一不留下假话的选项——客户端可以重签，重签是幂等的、不产生新记录。

## 6. 与账本的连接

`claimed → delivered` 这一次状态写入，**同时**产生两条账目。两条都不是客户端提交的，是从那条已经签过名的 `delivered` 行**推出来**的：

| 账目 | id | 字段从哪来 |
| --- | --- | --- |
| `give` | `g-<request_id>` | `from_agent_id` = `claim_agent_id`（认领方）；`to_agent_id` = `requested_by`（发布方）；`category`、`occurred_at` 照抄；`quantity`/`unit` 留 null（需求单没有数量字段，编一个数就是造假） |
| `receive` | `r-<request_id>` | `state='delivered'`、`occurred_at` 照抄、`evidence_uri` 照抄 |

两条同 `mutual_id = "m-" + request_id`，所以「一次互助」在账本里就是这一对。id 也是派生的、不带随机尾缀：任何拿到公开需求单的人都能算出这两个 id，不需要问运营方要一份对应表。

`give` 的给方是认领方，不是发布方——给东西的是那个把事做完的人。这也让 `/api/v1/entry` 那条「give 的给方必须就是签名主体」在转换里同样成立：提交 `delivered` 的就是认领方，转换用的是他的签名。

**为什么 `evidence_uri` 只在 `receive` 上。** 两件事的举证方不同：`give` 说「我给了什么」，是给方自述；`receive` 说「这次交付有凭据」，而凭据要受方认——第 04 步那条确认签的正是 `give` 的 `hash`。把凭据塞进 `give`，会让「给了什么」与「凭什么说给了」混在同一行。

`receive.evidence_uri` 与 `request.evidence_uri` 是**同一份值被复制**，不是引用链。两处各自独立可验；「指针的指针」在审计时只会多一层不信任。

**为什么签名不进条目表。** 签名签的是条目 `hash`，而 `hash` 又覆盖条目的全部字段——把签名放进条目就成了循环（`hash` 覆盖签名、签名覆盖 `hash`）。所以确认单独一张表 `entry_confirm`，它指向条目而不属于条目。副作用是好的：条目哈希完全不因「有人确认了」而变，确认可以被拒绝、可以被重签，账目一动不动。

**两个人各签了一次，但签的不是同一样东西。** 认领方签的是那条 `delivered` 提交（外层信封，`drawcommons-ingest` 域），`receive` 是它的函数；发布方签的是 `give` 的 `hash`（`drawcommons-confirm` 域）。所以 `receive` 没有第二次确认这一档——不是留待将来，是**不需要**：再签一次，签的还是同一句话。

**重复提交同一次交付怎么办。** 分两种，后果不同：

- **字段全一致** → 这是重试（网络断了、没收到响应）。回 `200` 与 `already: true`，附上上次那两条账目的位置与 hash，一个字节都不再写。重试不该被当成错误——那会让客户端以为交付失败了，而它其实成功过。
- **字段有一处不一致** → 这不是重试，是想改已入账的凭据。回 `422 DGB_LED_029`，凭据以第一次为准。append-only 本来也不给改的机会，但要说清是「不让改」而不是「撞车了」。

两条账目与那条 `delivered` 行在**同一个事务**里落库。分成两步就会留下「已交付但账上没东西」的中间态，而那个中间态没有任何人能修：`delivered` 不能重进（状态机不许），补账又没有入口。

**关单。** 发布方对那条 `give` 确认成功之后，这一单自动写一行 `closed`（完整复制上一行，只换 `state`——`DGB_LED_024` 要求 `closed` 也带 `occurred_at` 与 `evidence_uri`，关单不能把交付凭据弄丢）。这一步没有自己的接口，理由见 §2。

## 7. 结构落在哪里

表结构在 **`../ddl_v1.4.sql`**（增量，跑在 `../ddl_w4.sql` v1.3 之后）。本节只写「为什么是这几条约束」，不重复贴 SQL——同一段 SQL 贴两处，早晚会有一处是旧的；判据脚本直接执行那个文件，文档与实现因此没有第二个版本。

五组约束，各有各的失败形态：

| 组 | 拦什么 | 错误码 |
| --- | --- | --- |
| 状态机 | 跳号、非法迁移、终态再写、`open` 不在第 1 行、第 1 行不是 `open` | `DGB_LED_020` / `021` |
| 字段完备 | `claimed` 无认领方、`delivered` 缺时间或证据 | `DGB_LED_023` / `024` |
| 发布方固定 | 同一单的第 2 行换了个 `requested_by` | `DGB_LED_025` |
| 主体存在 | `requested_by` / `claim_agent_id` 未在 `party` 登记 | `DGB_LED_019` |
| append-only | 对 `request` 的 `UPDATE` / `DELETE` | `DGB_LED_012` / `013` |

`seq` 的连续性与状态迁移拆成两个触发器，且迁移触发器里带了 `seq = max+1` 前置条件。原因是 SQLite 对同表多个 `BEFORE INSERT` 触发器不保证执行顺序：两条同时满足时，报 020 还是 021 看运气，而「错误码确定」本身是判据的一部分。

两个视图：

- `v_request_current`：每组取最大 `seq`，是「当前状态」的唯一口径；
- `v_public_request`：在它之上按 90 天常量收窄终态条目，**不删行**。公开页与 API 只查这个视图。

## 7.1 怎么把记录送进来

状态行与条目都经写入面提交，契约在 **`ingest.md`**：请求体自签（SSHSIG，
namespace `drawcommons-ingest`）、四条 POST、`DGB_ING_*` 错误码。本文件只管
「记录长什么样」，那份只管「怎么送」——两件事分开写，是为了改其中一件时不必动另一件。

两条与本文件相关的硬约束（在那份里执行）：`open` 只能是第 1 行，所以重复提交 `open`
会被状态机挡下（`DGB_LED_020`）；`closed` 与 `expired` 不接受直写——前者要等双方签名与
两条账目都落库，后者由窗口到期触发。

## 7.2 谁来按这个键（责任，不是权限）

接口能验的是「这把钥签了这条请求」，验不了「这个人同意公开这件事」。两件事在 r6 里
都只剩最后一下，按给人：

| 动作 | 替人做会怎样 |
| --- | --- |
| 发需求（`open`） | 公开宣布「我这里缺东西」。append-only，`withdrawn` 只是状态，正文永久可读 |
| 认领（`claimed`） | 替人答应交付；占的是人的时间，不是 agent 的 |

所以 agent 该做的是「识别 + 拟稿 + 附证据」，不该做的是「代替他说我需要」或「代替他
答应给」。这一条**不进 DDL**——它是约定，执行者在客户端。写在这里是因为它约束的是
协议的使用方式，而使用方式也会被审计：一条由 agent 刷出来的需求，事后看不出与人发的
有什么区别，除非当初就说清「最后一下是人按的」。

## 8. 出界（明确不做）

撮合算法、推荐、排序、评分、纠纷裁决、资金、需求竞价。平台提供**信息**与**事实**：需求在哪、谁给过什么。谁该帮谁，不由平台决定。

## 9. 自己验

```bash
python3 evidence/check_spec.py            # 账本条目
python3 repo/deploy/app/selftest.py       # 写入面：自签、验签、重放、确认、入账转换（99 项）
# 需求单草案的正反例：ops 侧脚本（不在本仓库内发布）
```

`request.schema.json` 的两个 `examples` 必须全过；六类反例（open 带 seq=2、claimed 无认领方、delivered 缺证据、带 `amount_fen`、`need_desc` 空串、withdrawn 却带交付时间）必须全被拒。这条判据与账本的 `check_spec.py` 共用同一个校验器，不另写一套。
