# CONTRIBUTING

# 贡献指南与贡献者许可

> 本文件适用于本仓库的全部贡献：代码、规范、数据、文档。
> 提交即表示同意本文件的条款；不同意请勿提交。

## 1. 三类贡献，三种许可，一条规则

| 贡献类型 | 落点 | 对外许可 | 你授予的权利 |
| --- | --- | --- | --- |
| 代码 | `src/`、`scripts/`、部署配置 | Apache-2.0 | 著作权与专利的非独占、永久、全球、免费、不可撤回许可 |
| 规范与 schema | `spec/` | CC0-1.0 | 放弃著作权及邻接权（在法律允许范围内） |
| 数据 | `data/` | CC-BY-4.0 | 非独占、永久、全球、免费许可，含再许可 |
| 文档 | `docs/` | CC-BY-SA-4.0 | 同上，且改编作品须以同一许可发布 |

一条规则：**贡献的许可必须与目标目录的许可一致。** 你不得对 `spec/` 的贡献附加任何条件
（含署名要求），也不得对代码贡献附加比 Apache-2.0 更严格的条款。

## 2. 为什么用 DCO 而不是 CLA

本项目**不接受**著作权转让型 CLA（Contributor License Agreement）。理由不是偏好，是圈地通道：

| 机制 | 项目方获得的权利 | 能否据此转为专有 |
| --- | --- | --- |
| DCO（本仓库采用） | 仅"有权按仓库许可分发你的贡献" | **不能**。你保留著作权，项目方拿不到再许可权 |
| CLA 含著作权转让 | 著作权归项目方，可任意再许可 | **能**。一次转让即打开"把公共代码放进闭源版"的合法通道 |
| CLA 含再许可权（不转让） | 保留著作权，但授予项目方可换许可分发 | **能**。同上，且更隐蔽 |

R10 禁止把公共资产转为可排他。若采用第 2、3 行，R10 就只剩一句自我约束——**约束的对象恰好是持有再许可权的人**。
所以本仓库只签 DCO：它给了项目方分发所需的最小权利，且结构上无法用于闭源。

## 3. 签署方式（DCO 1.1）

每次提交须在 commit message 末尾加一行：

```
Signed-off-by: 你的真名 <你的邮箱>
```

该行表示你声明 DCO 1.1（全文见 `DCO`）中的四项。匿名或化名提交一律不予合并——
不是因为偏好实名，是因为**无法追溯的贡献无法在争议时被确认授权**。

**署名归属**：DCO 不转移著作权，你对所写的部分保留全部权利。所以**新增文件由你本人
在文件头署名**——`Copyright <年份> <你的名字或长期笔名> <邮箱>`，不要写「贡献者」这类
集体名：集体名在需要主张时指不到具体的人，第三方也无法据此履行「署名给谁」这个动作。
既有文件的版权行由维护者统一维护，你的改动仍以 `commit author` 与 `Signed-off-by` 为据。

署名不得写入账本数据与 `/api/ledger/export` 导出件——那里的字节被 sha256 锚定，写入
即改变锚值并使历史锚值全部失效。原因见 `NOTICE` 的「署名边界」一段。

## 4. 提交前自检（4 条，缺一不合并）

1. 文件头有 SPDX 标识（`SPDX-License-Identifier: <目标目录的许可>`）；
无法写注释的格式（`.json`）须提供同名 `.license` 伴生文件。
2. commit 带 `Signed-off-by`。
3. 未引入第三方代码；若引入，已在 `NOTICE` 中列明来源、版本、许可、修改。
4. 未新增"保留所有权利"、`All rights reserved`、或与目标许可冲突的条款。

## 5. 许可瑕疵上报

发现以下任一情形，开 issue 并标 `license-defect`，24 小时内不动该文件的内容：

- 某文件无许可归属（既不在归属表内，也无 SPDX 头）
- 某文件声明的许可与其所在目录不一致
- 出现 NC（禁商用）、ND（禁改作）类许可
- 出现来源不明的第三方内容

处置顺序：先在该文件头写 `SPDX-License-Identifier: NONE` 并移出构建，再查来源，
最后决定补授权或删除。**不得因为"先跑起来"而保留一个无授权文件。**

## 6. 规范类贡献的额外要求

`spec/` 的变更除 DCO 外，还须走公开评审（R10 形态②要求"变更须公开评审"）：

- 提案以 PR 提交，标题前缀 `[spec]`；
- 公示不少于 14 日；
- 至少 2 名非提案方评论，其中至少 1 名为外部实现者；
- 涉及核心字段增删的，须说明对既有实现的兼容影响。

未走公开评审的规范变更，即便合并也**不产生规范效力**——它只是一份提案。

## 7. 署名承诺与申领

提交被合并，就意味着我们对你作出了署名承诺。承诺落在四个位置，缺一个都算没兑现：

| 位置 | 形式 | 谁来写 |
| --- | --- | --- |
| 你新增的文件头 | `Copyright <年> <你的名字> <邮箱>` + SPDX | **你本人**，在提交里就写 |
| `CREDITS.md` §2 | 名字 + 署名文本 + 依据（commit）+ 登记日 | 维护者，合并后 14 日内 |
| `credits.json` | 机器可读的同一条记录 | 同上，与上一条同时改 |
| 发布包 | `CREDITS.md` 随包分发 | 出包钩子自动带上 |

**依据是硬要求。** 登记时写的 commit 必须真实存在——`repo_lint` 的 R12 会逐条验证，
写不存在的提交，体检直接红。这条不是形式主义：一个查不到出处的名字，在争议时
既不能证明贡献，也不能证明授权，等于没有。

三条我们不做的事，先说清楚：

1. **不把别人的贡献记在自己名下。** 合并时若改动了你的代码，改动部分另记一条，
   不吞进维护者的条目。
2. **不替你决定名字。** 用真名、长期笔名、还是要求隐去，由你说；我们只负责执行，
   并把执行记录留在 `CHANGELOG`。
3. **不承诺「永久署名」。** 署名权本身不受期限限制，但项目可能终止、域名可能失效。
   项目终止时，最后一版 tag 与当时的 `credits.json` 快照就是记录本身——我们不承诺
   一个我们已经无法维护的承诺。

**申领与异议**：发现名录漏了你、写错了你的名字、或你根本不想被列名，发信到
`admin@drawcommons.org`，30 日内处理。署名权可以放弃，不能被剥夺，也不能被
第三方代为处分——所以即使你要求隐去，git 历史里的 `author` 字段也不改写
（改写历史等于伪造记录）。完整规则见 `CREDITS.md` §6、§7。

**支持者不走这条流程。** 出资、出服务器、出场地不产生作品，没有著作权，也就没有
署名权；对他们的列名是约定，记在 `CREDITS.md` §4。把支持者写进贡献者名录，
等于承诺了一件法律上不存在的东西。
